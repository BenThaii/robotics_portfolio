Technical report · 01 / 05

Humanoid motion retargeting

Project: CMU mocap (BVH) → Unitree G1 humanoid, two retargeting pipelines Demo: https://benthaii.github.io/robotics_portfolio/motion-retargeting/ Scope: kinematics only. No dynamics, balance, contact reasoning or torque limits.

1. Problem

Human motion capture gives realistic joint motion, but a human skeleton and a G1 humanoid do not share the same proportions, axis conventions or reach envelope. Copying mocap joints onto the robot produces unreachable poses and unnatural motion. The task is to convert a BVH clip into a kinematically feasible robot joint trajectory that keeps the human's intent — where the hands and feet go, which way the body faces — while respecting the robot's joint limits.

Two pipelines are built and compared:

  • Stage 1 — own IK solver. A per-frame bounded least-squares solver written for this project.
  • Stage 2 — GMR. An external open-source model-based retargeter (Araújo et al., Stanford University, ICRA 2026, MIT licence), integrated and bridged to this project's data format. GMR is not authored here.

2. Pipeline

BVH file
  → parse skeleton FK                      → (T, J, 3) keypoint positions
  → axis map: BVH (x,y,z) → robot (z,x,y)  → z-up, x-forward (proper rotation)
  → 120 → 30 fps uniform subsample
  → per-limb proportion matching           → robot-scale keypoint targets
  → ground alignment                       → lowest ankle at standing height
  → pelvis yaw from mapped hip rotation
  → per-frame IK targets
  → warm-started bounded least squares     → joint trajectory (T, nq)
  → metrics (RMSE, saturation) + render    → side-by-side video

3. Key engineering decisions

Coordinate mapping. CMU BVH faces +z, y is up, left is +x. The G1 URDF is x-forward, y-left, z-up. The map (x, y, z)_bvh → (z, x, y)_robot is a proper rotation (determinant +1), so handedness is preserved. Verified from toe direction and root displacement — the dataset's own docs say "x forward", but the files do not follow that.

Per-limb proportion matching. One global scale cannot fit head, hands and feet at once: mocap skeletons are never proportioned like G1, and the una-dinosauria CMU conversions are also ~1/6 scale in arbitrary units. Each keypoint's pelvis-relative offset gets its own factor:

scale[task] = robot limb length / human rest-pose limb length

Legs use ankle distance (shared with the knee) so the contact-critical feet are exact. Root motion transfers with the mean leg scale, so the robot walks the human's path scaled to its own stride. Units cancel per limb; absolute BVH units are never trusted.

Two-bone arm construction. G1's arms are proportionally much shorter than a human's, so a scaled wrist target lands outside the reach envelope and the arm mushes toward whatever it can reach. Instead, each arm target is rebuilt every frame from the robot's current shoulder position (warm-start FK) using the human's upper-arm and forearm directions at the robot's own segment lengths:

elbow_target = shoulder + du * s1
wrist_target = shoulder + du * s1 + df_perp * s2

df is projected perpendicular to du because a 1-DoF elbow cannot hyperextend. The target is reachable by construction while still pointing where the human points, with the human's elbow bend.

Log-parameterized freeflyer. The configuration is reparameterized as z = [position(3), rotation-vector(3), joint angles]. scipy's Trust-Region-Reflective bounded least squares can then enforce joint limits exactly on the actuated joints while the base pose stays unbounded:

min_z  ½‖e(z)‖²     subject to   lower ≤ q_act(z) ≤ upper

Residual stack (one vector per frame, minimized jointly):

  • 3-D position tasks: head (d435 proxy), wrists (2.0), elbows, ankles (2.0), knees (0.2), pelvis (2.0)
  • pelvis yaw-only orientation: 0.5 · log3(Rz(yaw_des) · R_curᵀ)
  • posture regularizer: 0.02 · (q_ref − q_act) toward the previous frame

The posture row is what turns independent poses into a trajectory. Each frame warm-starts from the previous solution, both as initial guess and as posture reference. Solver: max_nfev=120, xtol=1e-10, finite-difference Jacobians inside TRF.

4. Results

OBSERVED, 2026-11-15. Six CMU clips, 120→30 fps. RMSE is unscaled 3-D position error of tracked keypoints versus BVH-derived targets, in centimetres. "Saturated" counts frames with at least one joint parked on a limit.

clip frames RMSE all ankle knee wrist head pelvis saturated
walk 688 3.4 cm 0.01–0.02 3.1–3.2 2.4–3.5 7.2 1.4 0
dance 281 4.6 cm 0.03–1.1 5.9–7.0 3.4–3.9 7.3 1.5 77
box 1399 1.7 cm 0.01–0.02 2.1–2.5 0.7–1.1 3.4 0.4 206
walk_multi 480 3.6 cm 0.03 4.4–4.5 4.5–4.6 4.6 2.0 77
kick 201 4.0 cm 0.03–0.91 4.4–7.0 3.0–4.2 5.4 1.5 47
jump 81 3.8 cm 0.03 4.9–5.1 4.3–4.9 4.3 2.0 0

Whole-body RMSE: 1.7–4.6 cm. Ankles track to 0.01–1.1 cm. Zero joint-limit saturation on walk and jump.

The saturated dance/box frames are expected, not hidden: G1's arms are much shorter than the mocap skeleton's, so extreme poses exceed the reach envelope. The IK parks joints on limits — the correct bounded optimum — and reports the residual.

Stage 2 (GMR), same yardstick but different targets:

clip RMSE all wrist
walk 16.5 cm 20.3
dance 17.3 cm 23.0
box 18.9 cm 27.7
walk_multi 15.8 cm 19.7
kick 13.1 cm 17.9
jump 11.9 cm 15.5

These two RMSE columns are not directly comparable. Stage 1 optimizes the exact position error being measured; GMR is rotation-weighted against its own scaled targets. GMR's advantage is visual — natural arm motion, grounded legs, plausible whole-body poses — not the number.

A fresh, never-configured 38.3 s basketball BVH retargeted live through GMR at ~380–550 FPS instantaneous on CPU in a single process. GMR is a real-time CPU retargeter.

5. Honest scope

  • Kinematics only. The output is a kinematically feasible trajectory, not a dynamically executable one. Whether it is physically trackable is answered in the separate physics-tracking report.
  • GMR is external open-source work (Araújo, Ze, Xu, Wu, Liu — Stanford, ICRA 2026, MIT): integrated, bridged and benchmarked here — not developed.
  • The ~70 Hz figure is the GMR paper's benchmark, not a locally measured rate. The locally measured 380–550 FPS is a different, render-free loop.
  • No employer, title, team or dates. Self-directed project, AI-assisted development.
